## Credentials: where they live and how to handle them

- Staging keys live ONLY in `.env.staging.local` at the repository root. It is git-ignored (`.env*`). Never commit it, paste it in chat, or copy it into a Vercel production environment.
- The anon (publishable) key is designed to be public. The **service-role key** bypasses all row-level security: use it only in server-side scripts (`tests/staging/*`), **never** in frontend code, never with a `NEXT_PUBLIC_` prefix.
- The database password was generated by Supabase at creation and is not stored anywhere. The SQL editor and the API do not need it. To use a direct database connection later, reset it in Dashboard > Project Settings > Database.
- Test identities in staging use synthetic `@staging.test` addresses with randomly generated passwords stored only in `.env.staging.local`. They are not real people and have no access to anything else.

## Applying migrations to staging

1. `npm run db:bundle` regenerates `supabase/setup-all.sql` from every migration, in order.
2. Open the project's SQL Editor, paste the file, run it once. Supabase warns about the `drop function if exists` lines: expected on a fresh project.
3. Verify with `node tests/staging/verify-schema.mjs` (tables, policies, buckets).

Apply a new migration on top of an existing staging database by pasting only that migration file. Production receives migrations only after staging passes and the owner approves.

## Inactivity pause (Free plan)

A Free project is **paused after about one week without activity**, and paused projects have no automatic backups. While paused, the API returns errors and tests fail.

To resume: Dashboard > the project > **Restore project** (takes a few minutes). Nothing is lost. Paused projects do not count toward the two-active-free-project limit, but restoring one needs a free slot (the organisation holds production plus staging = 2, so both can be active).
Any request to the API counts as activity, and so does running the staging checks regularly.

## Limits to remember (Free)

500 MB database, 1 GB file storage (shared with nothing else here, but production has its own), 50 MB upload limit, 5 GB egress, 50,000 monthly active users. A paid plan is not required for staging.

## Verifying against staging

```bash
npm run test:staging        # schema + policy check, then the product/order and the services backend workflows (real Auth, REST, Storage, RLS)
npm run test:staging:build  # builds the app with staging credentials into .next-staging (separate from the normal build)
npm run test:staging:e2e    # real browser workflow, desktop and mobile, as the synthetic @staging.test users
```

The browser tests seed fresh products each run, reset return policies, and leave nothing configured behind. They need `node tests/staging/workflow.mjs` to have been run once so the three test sellers are onboarded. The app server in the browser tests is started WITHOUT the service-role key.
